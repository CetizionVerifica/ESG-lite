# XI3 · Mapping memory (ESG-lite)

> Goes to `ESG-lite/src/imports/profiles/CLAUDE.md`. Depends on XI0. Blocks XI2 layer 1 (API shape only). Lane L2.

## Outcome
A client's confirmed mappings are remembered per company, so the next upload of the same layout maps itself; nothing learned from one client is ever served to another.

## Build
- Entity `ImportMappingProfile` + table per 01-contracts §3 (`migrate:ai-import` from XI0 creates it; this module adds indexes if needed).
- `src/imports/profiles/` router, controller, service: `GET /imports/mapping-profiles?fingerprint=` (and `company_id` for Superadmin), `DELETE /imports/mapping-profiles/:id`. Scope through `buildWriterContext`: a profile is returned only if `company_id` matches and (`site_id` is null or in `allowed_site_ids`). Anything else is 404, as plans are.
- Learning: `POST /imports/plans` stores `body.mapping` (a `MappingProposal` validated by XI0) on `import_plan.mapping` for `channel = "bulk_upload"`. On `onBatchCommitted`, a listener upserts one profile per sheet of that plan's mapping (key company + fingerprint + site + category), with `confirmed_by = event.user_id`, `uses + 1`. Activities confirmed in the proposal are stored in the profile; P23 writes stay with IM2's `save_mapping` rule (extended to Managers for their own sites if decision 5 is yes: `scope.ts` allows `save_mapping` when the match's site is in `allowed_site_ids` and the role is Manager).
- Audit log row per profile write (`entity_type: "import_mapping_profile"`).

## Must not
- Return or match a profile across companies, even on an identical fingerprint. Store cell values beyond the distinct texts of activity, site and category columns already in the proposal.

## Own tests
`ci/api/tests/xi3-profiles.test.cjs`: learn on commit; no learn on cancel or failed commit; fingerprint hit for the same company; company 2 Manager with the same fingerprint gets nothing; Manager of site 1 does not get a site-2 profile; delete rights; Superadmin needs `company_id`; `save_mapping` by a Manager on own site (if decision 5) and refused on another site.

## Audit rows
XI-05 memory tenant isolation, XI-06 learn-on-commit only.

## As built (XI3, 2026-10-14)
- **Table** `import_mapping_profile` (`src/entities/ImportMappingProfile.ts`, `migrate:mapping-profiles` = `src/scripts/createImportMappingProfileTable.ts`, idempotent, in `migrate:all`): uuid id, `company_id` (FK CASCADE), `site_id` (FK CASCADE, always set: imports are site-wise), `category_id` (FK CASCADE, NULL when the sheet takes its category from a column), `fingerprint` varchar(64), `sheet_proposal` jsonb, `confirmed_by` (FK SET NULL), `confirmed_at`, `uses`, timestamps; unique (company_id, fingerprint, site_id, category_id); indexes on company_id and fingerprint. XI0's `migrate:ai-import` did not create it, so this module ships its own script. It runs on the next container start like every other migration (`npm start` runs `migrate:all`, #126); nothing to run by hand.
- **Endpoints** (`src/imports/profiles/`, mounted by `src/imports/router.ts`):
  - `GET /imports/mapping-profiles?fingerprint=&site_id=` (+ `company_id` for a Superadmin, `IMPORT_COMPANY_REQUIRED` without it): the caller's company's profiles for that fingerprint and site, newest confirmation first, as `MappingProfile` rows. `site_id` is required (the query schema from XI0) and must be in the caller's `allowed_site_ids`, else `403 IMPORT_FORBIDDEN`; the client's `ai_import_enabled` switch must be on, else `403 AI_IMPORT_DISABLED_FOR_CLIENT`. Another company's profile for the same fingerprint is never in the answer (the query is keyed by the context's company). A User with category grants sees only profiles of granted categories; a column-category profile is trimmed to the granted values and activities (`visibleToCategories`).
  - `DELETE /imports/mapping-profiles/:id` ("Forget this mapping"): a Superadmin (no `company_id` needed, the profile names its client), the client's Admin, or the Manager who confirmed it (`confirmed_by`). A User, or a Manager who holds the site but did not confirm it, gets `403 IMPORT_FORBIDDEN`; a profile of another company, on a site outside the caller's scope, or a bad id is `404` (code `IMPORT_PLAN_NOT_FOUND`, message "Mapping profile not found."), as plans are. Not gated by the switch, so a client can still forget mappings after it is turned off. Answer `{ id, deleted: true }`.
- **Plan side**: the plans controller parses the body with `CreatePlanWithMappingBodySchema` (XI0 follow-up #124), so a malformed proposal is `400 IMPORT_VALIDATION` with paths `mapping.…` before the service runs. `validatePlanMapping` in `service.ts` (called by `plans/service.ts createPlan`) takes that parsed proposal and adds what a schema cannot know: `mapping` only with `channel = "bulk_upload"` (else `400 IMPORT_VALIDATION` at path `mapping`), only when the client's switch is on (`403 AI_IMPORT_DISABLED_FOR_CLIENT`), only for a `site_id` in the caller's scope (`403 IMPORT_FORBIDDEN { site_id }`), and only when every category it names (the fixed category, a column category's resolved values, each activity's `category_id`, excluded sheets aside) is in the caller's `allowed_category_ids_by_site` for that site (`403 IMPORT_FORBIDDEN { site_id, category_ids, sheet }`). Field keys and factor names are not checked here: XI2 checks them against the caller's context when a profile is used (01-contracts §2), and the engine resolves every plan row itself. One parse, one place for each rule. The parsed proposal is stored on `import_plan.mapping`. Plans without `mapping` are unchanged.
- **Learning** (`learnFromBatch`, subscribed to `onBatchCommitted` at boot by `registerMappingMemoryListener` in `src/index.ts`): runs after a commit succeeded, for `bulk_upload` plans with a stored proposal only. For each sheet that is not `excluded` and that wrote at least one row (a plan row in state `ready` whose `row_ref` sheet part is the sheet's name; a sheet whose rows were all issues or skipped teaches nothing): upsert the profile keyed company × fingerprint × site × category (`category.kind = "fixed"` → its id, else NULL; the match uses `IS NOT DISTINCT FROM` under `pg_advisory_xact_lock(hashtext(company:fingerprint))`, since the unique constraint treats NULL as distinct). `sheet_proposal` = the sheet with every `activities[].save_mapping` reset to false and `excluded` false; `confirmed_by` = the user who committed (`event.committed_by`, falling back to `created_by` for events from the internal python route), `confirmed_at` now, `uses + 1`. Two sheets with the same key in one workbook are one profile and one `uses` step. All profiles of one batch are written in one transaction. One `audit_log` row per write (`entity_type: "import_mapping_profile"`, action create | update | delete, `entity_id: 0` because the column is a number (bigint) and the id a uuid; `changed_fields` carries `profile_id`, `company_id`, `site_id`, `category_id`, `fingerprint` and `uses`, never cell text). Errors are logged and never undo or report against the commit. Cancelled plans, plans whose commit was refused, and Claude/API plans teach nothing.
- **Decision 5** (`plans/service.ts saveMapping`): a Manager may now `save_mapping` for a site in their `user_sites` (the existing scope check already refuses any other site with `IMPORT_FORBIDDEN`); Users still keep the match on the plan. The MAPPING_EXISTS rule and the `category_mapping` audit row are unchanged.
- Not stored: anything beyond the proposal (no row values, no sample rows). Not done here: the python side (XI2 reads `GET /imports/mapping-profiles` with the caller's token) and the FE "Last time you mapped this as…" (XI4).
- Tests: `ci/api/tests/xi3-profiles.test.cjs` (mapping validation and switch, learn on commit / not on cancel or failed commit, excluded sheets, column categories, fingerprint hit per company and site, Superadmin and Admin scoping, forget rights and audit, Manager `save_mapping` on own site and refused elsewhere, User never). `ci/api/tests/im2-plans.test.cjs` updated for the Manager rule. Audit rows XI-05, XI-06.
